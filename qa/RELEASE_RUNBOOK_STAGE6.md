## Точный порядок релиза, если все условия подтверждены

**Фаза A: перед действием**
1. Повторно сверить `main`, финальный SHA, статус всех проверок, Vercel
   target и отсутствие новых SQL-изменений. Запустить
   `qa/RELEASE_READONLY_PREFLIGHT.sql` для фиксации агрегатов и MD5 RPC.
2. Остановить только опасные новые финансовые действия CRM на согласованное
   короткое окно; не блокировать остальные приложения общей базы.
3. Сделать последнюю проверенную резервную копию/момент PITR,
   сверить snapshot и возможность восстановления вне production.
4. Записать baseline: количество заказов/оплат, кассовых и финансовых
   операций, hashes RPC, активные триггеры и дата в UTC.

**Фаза B: миграции** — отдельно согласованный доступ к базе
5. На тестовой Supabase проверить точно те же SQL 008/009, хеши и
   совместимость со старым клиентом. Отсутствие миграции 008 в production
   означает, что защищённая оплата **ещё не активна**.
6. Если staging прошёл и GO разрешён, применить проверенные миграции
   **008 → 009** с повторной сверкой хешей непосредственно перед запуском.
   SQL содержит fail-closed проверки; при расхождении остановиться.
   Не пропускать неуспешную миграцию и не применять часть набора.
7. Прочитать итоговые триггеры, роль зарплатной RPC, политики, метрики
   и логи. Выполнять финансовые тесты только безопасными сценариями;
   фиктивные реальные платежи не создавать.

**Фаза C: фронтенд** — после проверки обратной совместимости
8. Подготовить/ревьюировать один итоговый release PR к `main`.
   Требовать ревьюера, полные CI и проверки мобильного интерфейса.
9. В верном Vercel-проекте проверить staging/preview и затем
   опубликовать одну согласованную сборку. Использовать механизм
   поэтапного выпуска, если доступен. Прямой push в `main` без
   готового окружения и проверки — запрещён.
10. Проверить реальные чтения без изменения клиентских данных:
   вход и разграничение ролей, календарь, отображение финансов,
   штатные логи, загрузку PWA. Проверить, что у Рауля отсутствует
   кнопка проведения зарплатной выплаты.
11. Контролировать ошибки авторизации, платежей, кассы и БД. Проверить
   новые заказы/платежи только по подтверждённым фактическим действиям.

## Правила аварийной остановки

При любой ошибке блокировки оплаты, расхождении сумм, нарушении прав,
невозможности восстановить данные, изменении source MD5, отсутствии
действующей копии или неверном Vercel target — **STOP/NO-GO**.

- Визуальная ошибка: можно откатить **совместимый** frontend deployment,
  не откатывая всю базу. Совместимость предыдущего фронтенда с SQL 008/009
  должна быть доказана до релиза.
- Ошибка SQL: включить режим ограничения финансовых записей,
  сохранить диагностические сведения и выполнить согласованное исправление
  вперёд. Нельзя просто удалить платёжный guard: это вернёт обход оплаты.
- Порча данных: восстановить копию **в отдельную БД**, сравнить изменения
  после точки сохранения, выполнить адресную согласованную коррекцию.
  **Не запускать полный PITR** общей production Supabase:
  он затронет данные других приложений.
