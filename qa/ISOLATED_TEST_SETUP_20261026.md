# Безопасное изолированное тестирование «Работы»

Статус: **ОЖИДАЕТ СОГЛАСИЯ НА ПОЧАСОВУЮ СТОИМОСТЬ SUPABASE BRANCH.**
Создавать и подключать платную базу только после явного подтверждения владельца.

## Стоимость
Supabase `get_cost(type=branch)` для организации `gqmzaeojhnxymgzyjloe` вернул `amount=0.01344`, `recurrence=hourly` (USD). Ветка пока не создана, потому что нет отдельного согласия на эту цену.
Срок теста лучше ограничить одним днём и удалить ветку после завершения, если владелец согласует.

## Сейчас
- Основная база: `ma-svyaz-2`, `yedzfmibceboncrytbqz`.
- Vercel Preview: `feature/full-dark-responsive-redesign`, проект `rabota`.
- Предварительные сборки пока используют **ту же рабочую БД**. Нельзя выполнять запись реальных или тестовых данных через Preview.
- Supabase branch будет содержать схему/миграции, **без рабочих клиентов и заказов**.
- Для проверки входа потребуются тестовые аккаунты с ролью owner, manager и master, созданные исключительно в branch.

## Проверка перед любыми функциональными тестами

1. Создать Supabase branch и дождаться статуса HEALTHY.
2. Получить branch ref, URL и publishable key **из ветки**, не из production.
3. В тестовой версии `index.html` заменить **оба** значения `SUPABASE_URL`, `SUPABASE_KEY` на параметры из ветки.
4. То же самое сделать в `ai.html`.
5. В конфигурации Vercel для ветки Preview указать `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY` (используется `api/ai-chat.js`). Не изменять Production env.
6. Убедиться, что fallback в `api/ai-chat.js` не ведёт в Production при отсутствии Preview-конфигурации: настроить явный отказ запуска или обеспечить fail-closed механизм при TEST.
7. Убедиться, что `/rest/v1`, `/auth/v1`, `/functions/v1`, `/api/ai-chat` связаны с тестовой веткой. Поиск `yedzfmibceboncrytbqz` в тестовой сборке должен находить ссылки только в документации, не в исполняемом клиентском/серверном коде.
8. Не вставлять настоящие пароли, токены, service-role-ключи и личные данные клиентов в GitHub.
9. Создать тестовых пользователей через поддерживаемый механизм и назначить фиктивные роли. При первичном входе тестовая ветка не содержит production accounts; production credentials в ней не сработают.
10. Занести синтетические заявки: свободные/занятые окна, отменённые, завершённые, оплаченные/неоплаченные, запись без мастера.
11. Проверить owner/manager/master/без роли: отказы по RLS, вызовам RPC, доступу к чатам/финансам, ошибкам `NULL` и прямым REST/RPC вызовам. Никакие тестовые обращения к рабочему project id не разрешены.
12. Проверить создание и перенос, соперничество временных интервалов, дубликаты, отмены, платежи, финансы, распределение/сдачу денег, историю клиента, поиск, календарь и ИИ.
13. Проверить разные размеры экрана, браузеры и мобильную диктовку. Сохранить протокол результатов.
14. Подтвердить реальный механизм восстановления production backup через Supabase Dashboard. SQL-копия восьми функций — **не полная копия БД**.
15. Удалить тестовые ресурсы после согласования; ветка может тарифицироваться каждый час до удаления.
16. Публиковать Production можно **только по новому отдельному указанию владельца**.

## Релиз
Для выкладки потребуется убрать временные Preview-параметры/ограничения, повторно удостовериться, что Production остаётся на исходном Supabase project id, убедиться в наличии полного бэкапа и пройти регрессионные проверки.
