# Выпуск CRM «Работа»

## Разработка и независимая проверка

1. Разработчик создаёт рабочую ветку от `main` и открывает pull request с задачей, рисками, сценариями проверок и порядком миграции, если она нужна.
2. На кандидате запускается **CRM checks**. Обязательный итог **Release checks** собирает результаты JavaScript, мобильных Chromium/WebKit и изолированного PostgreSQL. Тесты прежних модулей сохраняются и используются для регрессии.
3. **CRM QA handoff** обновляет комментарий в pull request при новом кандидате. В комментарии находятся SHA, тестовый адрес и форма для дефектов. Для автоматического запроса ревью задайте аккаунты тестировщиков в GitHub Actions variable `CRM_QA_REVIEWERS`. Адресом стенда управляет `CRM_QA_URL`.
4. Опубликуйте кандидат в тестовом проекте Vercel. Сборка должна ссылаться на отдельный проект Supabase. На стенд передаются только схема и искусственные данные. Тестировщик сверяет адрес стенда и SHA кандидата, выполняет проверку и оставляет своё ревью по [инструкции тестировщика](TEST_STAND.md).
5. В правилах GitHub для `main` потребуйте pull request, статусы **Release checks** и **Independent QA**, а также свежее ревью. **Independent QA** проверяет решение аккаунта из `CRM_QA_REVIEWERS` на точном SHA. Включите сброс устаревших одобрений, требование одобрения последнего push и применение правил ко всем публикующим.
6. При запросе изменений верните pull request разработчику. Новый коммит проходит CI и QA заново. Решение **Approve** относится к проверенному SHA.

Правило GitHub описано в [github-main-rules.json](staging/github-main-rules.json). Для первого включения администратор настраивает `CRM_QA_REVIEWERS` и `CRM_QA_URL`, а после проверки инфраструктурного PR переносит конфигурацию в `main`. Затем проверьте, что GitHub видит оба статуса, и включите правило. Доверенная проверка ревью использует рабочие процессы из основной ветки.

## Тестовая сборка Vercel

- Создайте отдельный пустой Supabase-проект для QA. В его настройках Auth выключите публичную регистрацию и оставьте вход по паролю для заранее созданных тестовых аккаунтов. Проверьте, что в проекте отсутствуют внешний SMTP, вебхуки и провайдеры уведомлений.
- Установите схему `qa/staging/schema.sql` в выбранном QA-проекте. Перед SQL в том же запросе задайте `SET rabota.qa_project_ref = '<QA project ref>';`. Затем создайте три подтверждённые тестовые учётные записи с `scripts/provision-qa-users.mjs` и примените `qa/staging/seed.sql`. Скрипт Auth берёт `QA_SUPABASE_PROJECT_REF` и `QA_SUPABASE_ADMIN_KEY` отдельного проекта, а также путь к закрытому JSON с тремя паролями. Локальный прогон схемы, данных, прав и восстановления выполняется командой `bash qa/staging/rehearse.sh`.
- Инструмент сборки `scripts/build-qa.cjs` принимает `QA_SUPABASE_URL` и `QA_SUPABASE_PUBLISHABLE_KEY` отдельного тестового проекта. Сборка создаёт `.vercel/output`, совместимый с Vercel Build Output API. Запустите команду из чистого checkout нужного коммита. Сборка сверяет указанный SHA с Git и отклоняет незакоммиченные файлы.

  ```sh
  node scripts/build-qa.cjs
  ```

- Деплой выполняют из отдельного каталога-артефакта, привязанного к `rabota-qa`. Перед отправкой сверьте ID именно тестового проекта. Подготовить такой каталог можно командой `node scripts/build-qa.cjs --format source --out /tmp/rabota-qa-candidate`. Постоянным адресом QA служит production-алиас тестового проекта.
- После выкладки проверьте, что `/qa-build.json` возвращает полный SHA кандидата и origin тестовой Supabase. На странице должны быть видимы отметка тестовой среды и форма входа, а WhatsApp, push и ИИ должны оставаться внутри тестового сценария.
- Запустите `node scripts/verify-qa-live.mjs /закрытый/путь/qa-passwords.json` с переменными `QA_VERCEL_URL`, `QA_SUPABASE_URL`, `QA_SUPABASE_PUBLISHABLE_KEY` и `QA_BUILD_SHA`. Проверка сверяет адрес базы, опубликованный SHA, политику сетевых запросов и права трёх тестовых пользователей. Пароли читаются из файла с правами 600 за пределами репозитория.
- Публичный ключ тестового проекта поставляется браузеру в сборке. Секрет администратора Supabase нужен только в закрытом окружении для подготовки тестовых пользователей. Перед подключением новой услуги проверяйте тариф и согласовывайте дополнительные платные расходы.

## Контроль перед выпуском

- Сверьте SHA и успешные **Release checks** и **Independent QA** для того же кандидата. Для изменений схемы приложите результаты прогона точного SQL на тестовой Supabase и проверки совместимости с предыдущим клиентом.
- Запишите адрес и ID действующего Production-деплоя Vercel вместе с исходным SHA. Проверьте, что он доступен для отката.
- Перед миграцией сохраните проверенный резервный снимок. Для контрольного восстановления рабочих данных используйте отдельный закрытый экземпляр с ограниченным доступом. Для общего QA-стенда используйте искусственный набор. В закрытой записи о выпуске укажите проект и время UTC, объём копии, контрольную сумму и результат восстановления. В pull request достаточно статуса и ссылки на закрытую проверку.
- Для тестовой базы сохраните воспроизводимые миграции и искусственные данные в Git. Учётные записи и ключи храните в закрытом хранилище. Перед сбросом базы зафиксируйте источник и целевой QA project ref и убедитесь, что он соответствует конфигурации тестового Vercel.
- Используйте существующий workflow **Safe release step 5 - disposable backup restore** для тренировки восстановления синтетического набора. Тест сравнивает записи и права на другом экземпляре PostgreSQL 17.
- Для общей рабочей базы согласуйте объём резервного копирования с владельцем. Снимок только таблиц CRM полезен для сверки этих таблиц. Для восстановления всего проекта нужна отдельная проверка полноты, включая настройки Auth, Storage и другие приложения. [Резервное копирование в Supabase](https://supabase.com/docs/guides/platform/backups)

После успешных проверок выпускайте из защищённой `main`. Проверьте в Vercel привязку рабочего домена к ожидаемому SHA и статус Ready. Публичная проверка выпуска читает HTML и изменённые ресурсы, а функциональная проверка использует синтетические записи на QA-стенде. Запишите ссылки на pull request, результаты тестов, тестовый и рабочий деплои.

## Откат

1. Определите, совместима ли предыдущая сборка Vercel с действующей схемой. Если совместима, восстановите предыдущий деплой и проверьте рабочий домен, версию и доступность основных маршрутов. Зафиксируйте откат в pull request.
2. При несовместимой миграции сохраните уже записанные операции и подготовьте совместимое исправление схемы. Для восстановления используйте отдельный экземпляр, проведите сверку изменений после момента копии и согласуйте перенос этих изменений.
3. Для тестового стенда примените предыдущую опубликованную сборку тестового проекта Vercel. В случае повреждения тестовых записей разверните проверенный снимок тестовой базы или повторно создайте тестовые данные из миграций и seed. Проверьте вход всех трёх ролей и сверку баланса.

См. [откат Vercel](https://vercel.com/docs/deployments/instant-rollback) и [восстановление Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).
