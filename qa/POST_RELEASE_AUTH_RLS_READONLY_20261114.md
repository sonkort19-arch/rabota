## Read-only проверка RLS непосредственно в production Supabase

Для проверки использовалась `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`; временно выставлялись SQL-роль `authenticated` и claim `request.jwt.claim.sub`. Каждая проверка завершалась `ROLLBACK`. Это проверка исполняемых SQL/RLS-политик **без настоящего подписанного JWT и без PostgREST-запроса**.

| Контекст | Результат |
|---|---|
| `anon` | Прямой SELECT `rabota_orders` возвращает отказ доступа `42501`; данные не прочитаны |
| Вымышленный неизвестный `authenticated` | 0 заказов, 0 финансовых операций, 0 записей по кассе |
| Активный владелец | Роль определена как `owner`; доступно 41 заказ, 27 финансовых операций, 15 записей по кассе |
| Активный мастер с именем Рауль | Роль `master`; видно 41 заказ, у 0 из видимых заказов `assigned_user_id` отличается от `auth.uid()`. Видны 27 финансовых операций и 15 кассовых записей; у 0 видимых финансовых операций другой `master_user_id` |

**Ограничения интерпретации:** все 41 видимый мастеру заказ в текущем снимке могут быть назначены одному мастеру. Поэтому это *не доказательство* отсутствия утечек при добавлении второго мастера. SQL-моделирование роли не заменяет вход реальных тестовых `owner/manager/master` через Supabase Auth/JWT/PostgREST. Никакие реальные записи не изменялись, персональные данные не выгружались.

## Финансовые условия, оставшиеся без подтверждения

1. Реальная резервная копия всей общей Supabase (включая другие приложения), шифрование и **проверенное восстановление** на другом окружении.
2. Настоящий отдельный Auth/JWT/PostgREST staging на синтетических пользователях и заказах.
3. Сверка 20 старых оплаченных заказов без полного набора реквизитов оплаты, исторических распределений и ручных выплат с первичными документами; без автоматических корректировок.
4. Независимое SQL-review миграций `008 → 009 → 010` и подготовленный план отката. Отдельное разрешение на применение к рабочей базе.

Результаты SQL fixture/CI из PR #74 остаются действительными лишь для вымышленного PostgreSQL 17. Они **не являются подтверждением безопасности применения к реальной общей базе**.

Пока эти условия не выполнены: **не выполнять SQL 008/009/010**, не менять платёжную историю, не развёртывать CRM в посторонний Vercel-проект `grafik`.
