## Риск назначения мастера: новые ограничения оплаченных заказов

Прочитаны существующие тела RPC `rabota_approve_master` и
`rabota_provision_master` (без их изменения):
обе функции выполняют `UPDATE public.rabota_orders` с переназначением
`assigned_user_id` по имени мастера; `rabota_provision_master`
делает это **без фильтра по `paid`**.

Миграция `008` запрещает изменение назначения уже оплаченных заказов.
Поэтому создание/повторное обеспечение учётной записи мастера, чьё имя совпадает
с историческими оплачиваемыми заказами, может получить отказ транзакции.
Этот сценарий надо воспроизвести в изолированной Supabase с реальными RLS/Auth,
а не ослаблять защиту финансов в production.

При агрегатной проверке в момент запроса: 0 оплаченных заказов с именем
мастера, назначенных другому активному мастер-аккаунту; 0 оплаченных заказов
с указанным мастером, но без `assigned_user_id`. Это не доказывает
безопасность будущих замен и регистрации мастеров.
