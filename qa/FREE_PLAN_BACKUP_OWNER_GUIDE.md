# Как сохранить базу CRM «Работа» на тарифе Supabase Free

Дата проверки: 14 ноября 2026. Production Supabase: `ma-svyaz-2`,
ref `yedzfmibceboncrytbqz`, PostgreSQL 17.6. Проект принадлежит
организации с тарифом **Free** (подтверждено Supabase MCP).

**Это инструкция, а не готовая резервная копия.** Скрипты в этом
репозитории сами не подключаются к production. Нельзя отмечать
`production_backup_restore` как выполненный, пока настоящая копия
не создана, не защищена и не восстановлена отдельно.

## Проверенные особенности проекта

Read-only SQL на момент проверки: 57 таблиц в `public`, среди них
11 таблиц `rabota_*`; 2 учётные записи `auth.users`;
1 Storage-бакет и 0 Storage-объектов. Это агрегаты; ни данные
клиентов, ни пользователи в репозиторий не экспортированы.

Здесь несколько приложений Mobile Angel, поэтому **нужен backup всей
общей базы**, а не только 11 таблиц «Работы».

Официальная документация Supabase (обновлено 5 ноября 2026):
https://supabase.com/docs/guides/platform/backups
У Pro, Team и Enterprise есть автоматические ежедневные копии; на Free
нужно организовать свой экспорт и хранение вне платформы.

## Что сделать на доверенном компьютере владельца (без отправки паролей)

1. Откройте https://supabase.com/dashboard/project/yedzfmibceboncrytbqz
   и убедитесь, что выбран проект **ma-svyaz-2**, а не другая база.
2. Установите Supabase CLI и Docker Desktop. В терминале выполните
   `supabase --version` и `supabase db dump --help` — подтвердите
   доступные параметры. Актуальная инструкция:
   https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore
3. На странице проекта нажмите **Connect**, выберите **Session pooler**
   (либо direct при наличии IPv6) и получите строку подключения.
   Данные подключения **никогда не публиковать**, не вставлять в чат,
   GitHub Issues, PR, Actions или снимки экрана.
4. Создайте папку для приватной копии **за пределами GitHub и
   синхронизируемых публичных папок**, ограничьте доступ. Установите
   права файлов `600`, папки `700` (на macOS/Linux).
5. Используйте три команды из официальной документации Supabase
   (введите реквизиты подключения **только на своём доверенном
   устройстве**, не коммитьте файлы):
   ```bash
   # Параметры сверить с выводом установленной версии CLI --help
   supabase db dump --db-url "$PRIVATE_DB_URL" -f "$PRIVATE_DIR/roles.sql" --role-only
   supabase db dump --db-url "$PRIVATE_DB_URL" -f "$PRIVATE_DIR/schema.sql"
   supabase db dump --db-url "$PRIVATE_DB_URL" -f "$PRIVATE_DIR/data.sql" --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes"
   ```
   `PRIVATE_DB_URL` и `PRIVATE_DIR` здесь обозначают **локально
   установленные приватные переменные**, а не значения для отправки
   помощнику. Команды показывают методику; я их не запускал.
6. Убедитесь, что все файлы существуют и не пусты. Выполните локальный
   `bash scripts/verify-supabase-dump-local.sh "$PRIVATE_DIR"` для
   контрольных SHA-256. Скрипт **не загружает данные в интернет** и
   не выводит содержимое SQL. Файл `SHA256SUMS` храните вместе
   с архивом. Если утилита отсутствует/проверка не прошла — STOP.
7. Зашифруйте архив надёжным инструментом и храните минимум одну
   копию вне компьютера, отдельно от проекта. Пароль от архива
   хранить в менеджере паролей, не в репозитории.
8. **Требуется тест восстановления** на отдельном проекте/экземпляре,
   никогда не на рабочем `ma-svyaz-2`. Не применять команды
   восстановления из документации до проверки владельцем. Для нового
   платного проекта сначала проверить стоимость и согласовать её.
9. Сравните таблицы и записи, права, триггеры, RPC, историю заказов,
   кассу, начисления, авторизацию владельца и мастера. Три SQL-файла
   Supabase CLI **не следует считать доказательством полного
   восстановления Auth/Storage без теста**. Настройки Auth,
   секреты, Edge Functions и Storage-файлы учитывать отдельно.
   На момент проверки Storage-файлов было 0, но перед экспортом
   количество нужно пересчитать.
10. Зафиксируйте для себя: UTC-время создания, срок хранения,
   контрольные суммы, результат восстановления, ответственного,
   фактический RPO/RTO. **Не храните настоящие деньги/контакты
   клиентов в отчёте GitHub.**

## Если команда прервалась

При любой ошибке CLI, отсутствии файла, недостатке места, отказе
шифрования или восстановлении с расхождениями — **NO-GO**.
Не стирайте старые копии и не отключайте проверки прав.

## Отдельный вопрос — адрес Vercel

Поле `homepage` репозитория
https://github.com/sonkort19-arch/rabota содержит
`https://rabota-rust.vercel.app`. Это **декларированный адрес**,
а не доказательство текущего production. Подключённый Vercel доступ
имеет только к другому проекту `grafik`. Проверить принадлежность
`rabota-rust` и фактический deployment сможет владелец после
подключения **того Vercel-аккаунта/команды, где размещена «Работа»**.
Никогда не выпускать CRM в `grafik`.

Состояние работы: **NO-GO, реальные данные не изменены, backup не создан.**
