# Шаг 1 безопасного выпуска CRM «Работа»: исправленный PR №58

Статус: **только проект SQL в GitHub**. База production Supabase
`yedzfmibceboncrytbqz`, GitHub `main`, Vercel и клиентские данные
не изменены. Исходный PR №58 не изменён: доработки подготовлены
в отдельной ветке `feature/stage-01-paid-guard-hardening-20261114`.

## Что обнаружено при проверке реальных функций (только чтение)

- `rabota_record_order_payment` проверяет роли, сумму, способ и
  отсутствие предыдущей оплаты, блокирует строку заказа `FOR UPDATE`.
- `rabota_cash_distribute` проверяет мастера Рауля, назначение, статус
  и отсутствие коллекции, меняет заказ и записывает два начисления
  в одной транзакции.
- Исходный PR №58 защищал `OLD.paid=true`, но позволял владельцу/
  менеджеру напрямую писать `paid=true` в неоплаченный заказ.
- Первоначальный guard мешал RPC менять `status/completed_at` для
  уже оплаченного заказа с `cash/master`, которому ещё требовалось
  распределение. Это исправлено.
- В текущей production-базе 41 заказ, из них 29 оплаченных;
  20 старых оплаченных заказов не имеют полного набора реквизитов.
  Они **не пересчитываются и не дополняются** этой миграцией.
- Важно: действующая `rabota_cash_distribute` сама запрещает
  распределение уже оплаченных заказов с полностью пустыми
  `payment_method/payment_received_by`. Это существующее ограничение.
  Миграция его не обходит, иначе могла бы повторно начислить выплаты.
  Такие исторические случаи требуют отдельной сверки с владельцем.

## Реализация

`sql/008-protect-paid-orders.sql`:
1. Перед любой заменой SQL проверяет PostgreSQL 17, наличие действующего
   cash guard и неизменность двух исходных RPC по MD5 `pg_proc.prosrc`.
   При расхождении весь скрипт останавливается до изменения функций.
2. Сохраняет код существующих `SECURITY DEFINER` RPC, добавляя
   вокруг ровно одного `UPDATE rabota_orders` в каждом из них
   транзакционный маркер `rabota.order_payment_intent`; после UPDATE
   маркер очищается.
3. Новый `SECURITY INVOKER` триггер `BEFORE INSERT OR UPDATE OR DELETE`
   блокирует создание оплаченной записи и прямое редактирование оплаты,
   защищает оплаченные строки от редактирования и удаления.
4. Разрешённая первичная оплата требует точной формы перехода, совпадения
   пользователя и роли с существующими проверками RPC, а также
   эффективной роли владельца SECURITY DEFINER функции. Подделка
   одного только параметра маркера не позволяет сделать прямой PATCH.
5. Разрешённое распределение наличных проверяет, что заказ назначен
   Раулю и ещё не распределён; для ранее оплаченного `cash/master`
   допускается только завершение и заполнение недостающих реквизитов
   существующей процедурой. Цена, клиент, мастер и назначение не меняются.
6. Техническое обновление `updated_at` уже оплаченного заказа оставлено.
7. Никакие `rabota_*` таблицы, существующие RLS-политики и финансовые
   записи не мигрируются, не удаляются и не изменяются.

## Проверки

- `tests/paid-order-guard.test.cjs`: статические контрактные проверки;
- `tests/sql/paid-guard-fixture.sql`: полностью вымышленные пользователи,
  заказы, оплаты и роль-мастер в отдельном PostgreSQL 17;
- `tests/sql/paid-guard-scenarios.sql`: реальные SQL-триггеры и RPC
  проверяются с правами owner, manager, master и anon;
- `tests/sql/paid-guard-rpc-drift.sql`: отдельная тестовая БД с
  изменённой процедурой — миграция обязана прерваться без установки защиты;
- `.github/workflows/stage01-paid-guard-v2.yml`: две независимые проверки:
  Node 22 и PostgreSQL 17.

Проверяются: прямые INSERT/UPDATE с `paid=true`, даже с поддельным
`SET`-маркером; POST оплаты только через RPC; повторная оплата;
изменение цены, отмена и удаление после оплаты; обычные неоплаченные
заказы; распределение наличных ровно один раз; старый заказ без реквизитов
без повторного начисления; ранее оплаченный `cash/master` с неполными
реквизитами; чужой мастер; анонимный пользователь; совместимость со
старым cash guard.

## Ограничения

- Успех тестов в **изоляции** не доказывает полный успех на настоящих
  пользовательских записях и всех комбинациях ролей, RLS и расписания.
- Не тестировались одновременные реальные сессии под нагрузкой,
  восстановление из бэкапа, iPhone и интеграция всех этапов 2–10.
- Маркер предназначен для контролируемых серверных RPC. Нужно сохранить
  запрет на выдачу пользователям произвольного исполнения SQL и регулярно
  проверять права SECURITY DEFINER функций.
- Не применять миграцию, если какой-либо из хешей RPC поменяется:
  сначала повторить аудит и пересобрать исправление.
- Отмена триггера после реального выпуска **снова откроет** риск прямой
  оплаты. Поэтому сначала готовить исправление вперёд, резервную копию и
  план блокировки операций. Аварийный откат — отдельное согласование.

   трёх ролей, проверка отсутствия влияния на другие приложения общей базы.
4. Документирование 20 legacy оплат и расхождений автоматического журнала
   выплат в финансовой сверке.
5. Выпуск в production — только после отдельной команды пользователя
   «на основную» и проверенной резервной копии. Слияния PR пока запрещены.
