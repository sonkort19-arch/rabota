Дата подготовки: 2026-11-14. **Статус: процедура на синтетической базе испытана; реальный backup/restore ещё НЕ подтверждён.**

Production: Supabase project `ma-svyaz-2` (PostgreSQL 17). Это **общая база** с другими приложениями Mobile Angel.
Frontend: GitHub `sonkort19-arch/rabota`, текущий `main` на момент подготовки релиза: `3c3e037b9a97ba74544af2fe337e09175cb603d7`.

## Что реально проверено

- На одноразовом **PostgreSQL 17** с вымышленными данными из `tests/sql/roles-stage3-fixture.sql` установлены
  две предложенные миграции `008` (защита оплаты) и `009` (выплаты только владельцем).
- Созданы/проверены 8 вымышленных заказов, из них 5 оплачены,
  1 кассовое распределение и 3 финансовые операции.
- Получен архив `pg_dump --format=custom`. Сверены SHA-256 и архивный
  каталог `pg_restore --list`; искусственная порча меняет контрольную сумму.
- Архив восстановлен `pg_restore --single-transaction --exit-on-error`
  в **отдельную новую тестовую БД**.
- Совпали детерминированные контрольные отпечатки строк заказов, участников,
  начислений, распределений, RLS, политик, триггеров и SQL-функций.
- В восстановленной БД повторно проверены:
  прямое изменение оплаченного заказа запрещено; мастер видит свою зарплату,
  но не может сам оформить выплату.
- Временные файлы удаляются после работы; никаких дампов, паролей и клиентских
  строк не выгружается в GitHub, ChatGPT или артефакты Actions.
- Код: `tests/step05-backup-restore.sh` и `.github/workflows/release-step05-backup.yml`.

**Важно:** этот тест не создаёт восстановимую копию настоящего проекта.
Одноразовый архив удаляется вместе с GitHub runner. Он подтверждает только
работоспособность проверенной методики на синтетическом PostgreSQL.

## Что перед production обязательно выполнить у поставщика Supabase

  Подтвердить, что существует успешная резервная копия с конкретной датой,
  временем и сроком хранения. Проверить PITR, если включён.
  **Я не могу подтвердить это через подключённый инструмент:** функции
  просмотра списка backup-файлов в текущем подключении нет.
- [ ] Перед любой финансовой миграцией согласовать окно выпуска и ограничить
  новые записи CRM на краткое время. Не останавливать другие приложения
  общей базы без отдельного согласования.
- [ ] Выполнить защищённый экспорт базы с помощью Supabase CLI (если нужен
  независимый переносимый логический backup) или подтверждённой функции
  Dashboard. Запуск только у владельца/администратора в доверенном окружении.
  Примеры из документации, **не запускать без проверки `supabase db dump --help`**:

  ```bash
  supabase db dump --db-url "$SECURE_DATABASE_URL" -f "$SECURE_BACKUP_DIR/roles.sql" --role-only
  supabase db dump --db-url "$SECURE_DATABASE_URL" -f "$SECURE_BACKUP_DIR/schema.sql"
  supabase db dump --db-url "$SECURE_DATABASE_URL" -f "$SECURE_BACKUP_DIR/data.sql" --use-copy --data-only
  ```

  `SECURE_DATABASE_URL` и содержимое копии конфиденциальны. Никогда не
  присылать строку подключения, пароль, дамп, платежные и клиентские
  данные в чат, pull request или публичную сборку. Шифровать архив,
  хранить вне репозитория с ограничением доступа.
- [ ] Убедиться, что архивы читаются, совпадают контрольные суммы,
  зафиксирована точная UTC-дата/момент копирования и ответственный.
- [ ] Восстановить **действительную** копию в изолированный Supabase-проект
  или другую совместимую PostgreSQL-среду, не имеющую доступов к production.
  Новый Supabase-проект может быть платным; создание требует отдельного
  согласования стоимости и организации.
- [ ] Сравнить число и контрольные суммы записей `rabota_*`, связь

## Сценарий безопасного отката

1. **Ошибка интерфейса**: вернуть заранее проверенное предыдущее
   развертывание Vercel, не изменяя таблицы. Не возвращать старый фронтенд,
   если его контракт несовместим с уже применённой SQL-миграцией:
   сначала проверить обратную совместимость.
2. **Ошибка SQL-миграции**: остановить только опасные новые записи CRM,
   собрать диагностику и по возможности сделать контролируемое исправление
   вперёд (forward-fix). Не удалять защитный триггер без нового решения,
   иначе снова откроется прямой обход оплаты.
3. **Потеря/порча данных**: восстановить **проверенную** копию в отдельную
   базу, сверить изменения после времени копирования и только потом
   выполнять согласованное адресное восстановление данных `rabota_*`.
4. **НЕ выполнять полный PITR/restore рабочей Supabase вслепую**:
   эта база обслуживает другие приложения Mobile Angel. Полный откат
   может удалить их новые заказы, пользователей или платежи.
5. Все действия фиксируются: время, коммит, применённая SQL-миграция,
   число заказов/операций до и после, кто одобрил и результат проверки.
