## Как выполняется каждый час

1. Читать `qa/autonomy-progress.json`, актуальный HEAD `main` и только релевантные живые показатели. Сверять уже созданные ветки/PR, не создавать дубли.
2. Выбирать **одну** самую раннюю ещё не завершённую задачу и делать маленькое проверяемое изменение; не проводить косметические правки ради отчёта.
3. Для кода: отдельная ветка → небольшой PR → тесты Node + Chromium/WebKit на **том же HEAD**, проверка совместимости, diff и регрессий. Не включать реальных клиентов в тестовые данные.
4. Только низкорисковые изменения, не меняющие договорённости бизнеса/права/платежи, могут переходить в `main` после действительно успешных обязательных проверок и подтверждения целевого deployment/совместимости; оставить кодовую точку отката. Если предпосылки не выполнены, PR остаётся открытым.
5. Фиксировать фактические доказательства, выполненные и заблокированные этапы в `qa/autonomy-progress.json`. Не считать `CI started` равным `CI success`, не считать `merged` равным `deployed`.
6. Уведомлять владельца **только при завершении этапа, обнаруженном рабочем сбое, единственном необходимом действии с его стороны или итоговом завершении**. Не слать ежечасные уведомления «ничего не изменилось». В уведомлении: результат, ссылки, `X/10` этапов и сколько осталось.

## Строгие ограничения автономии

- **Не выполнять** в общей рабочей Supabase `INSERT/UPDATE/DELETE`, миграции/DDL/RPC с записью, изменение RLS/ролей, кассы/зарплаты, клиентов, Auth-пользователей и других приложений без отдельного предметного разрешения и плана восстановления. Уже выпущенные SQL 008–010 не повторять.
- Не создавать платные Supabase/Vercel ресурсы, не менять домен, секреты, тарифы, GitHub-права или настройки доступа без отдельного согласия.
- Не отправлять клиентам WhatsApp/Instagram/Telegram/Авито сообщения и не создавать реальные заявки; только локальные/синтетические сценарии.
- При ошибках CI, невозможности проверить Vercel target, небезопасных изменениях или отсутствии GitHub admin — **остановить выпуск этого изменения**, сохранить результаты и продолжить иной безопасный пункт; при блокере, требующем владельца, сообщить один раз.
- Ни один тест на synthetic Postgres не заменяет реальный JWT/PostgREST и физический iPhone.
- Стараться достигать цели автономно, но **не обещать** гарантированного окончания без внешних прав/тестов. Отчитываться о фактах.
- Если аварийная ситуация в production, сначала только диагностика/ограничение дальнейших действий; финансовые исправления без плана отката не применять.
