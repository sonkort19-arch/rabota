# Безопасное внедрение PR №25

Статус: **подготовлено, к production не применялось**. Продолжается исходный PR №25, не новый аудит. Ни одна команда ниже не даёт агенту разрешение на production SQL, merge или deploy. Каждая такая операция ждёт отдельного подтверждения владельца.

## 1. Что сверено с production

09.11.2026 повторно прочитаны только каталоги схемы и 20 строк для ручной сверки. PostgreSQL **17.6**; RLS включён на 10 таблицах. Изменяемые определения RPC/триггеров совпадают с исходным snapshot PR. В приватном `/workspace/rabota-private/production-schema-contract.json` сохранены типы/nullable/default полей, ограничения, индексы, политики, ACL и хеши функций без бизнес-строк. UUID конкретного мастера в политике обезличен. Секреты не выгружались.

Публичный `000-preflight.sql` проверяет затрагиваемые функции/колонки, RLS основных таблиц и отсутствие дублей активных заказов по лиду. Полная сверка ограничений, индексов и политик сохранена отдельно в приватном `/workspace/rabota-private/full-production-preflight.sql`; оператор должен выполнить её непосредственно перед релизом. При расхождении останавливается. Он допускает исходное определение C1 и уже исправленное C1; **не предназначен для повторного запуска после 002**, которая закономерно меняет контракт. В изолированной БД проверено, что drift колонки действительно блокирует продолжение. Сам 001 имеет независимую проверку хеша RPC и может рассматриваться для срочного отдельного выпуска.

Безопасный OPTIONS-запрос к production Data API подтвердил HTTP 200 и разрешение `x-rabota-client` / `x-rabota-order-version` в CORS. Запрос не содержал записи или оплаты. Это проверка gateway, а не замена авторизованного сквозного теста PostgREST.

## 3. Резервная копия: что готово и чего ещё нет

Подготовлен `scripts/backup-db.sh`: полный логический custom archive доступных объектов БД, роли без паролей, SHA-256 и оглавление. Libpq-реквизиты поступают через защищённое окружение/PGPASSFILE; пароли не передаются в аргументах, Git или чате. Экспорт запускается с default_transaction_read_only=on, каталогами/файлами с приватными правами и запретом хранения внутри checkout. При ошибке остаётся `.partial`, который не считается готовой копией. Серверный `COPY FROM PROGRAM` и чтение файлов сервера не используются.

**Реальный production archive ещё не создан и не восстановлен.** В среде нет libpq credentials. Подмена этого факта schema-only fixture или синтетическим прогоном недопустима. Перед полноценным релизом владелец/оператор должен предоставить доступ через защищённое хранилище окружения либо выполнить экспорт самостоятельно и подтвердить успешное восстановление его копии в отдельном совместимом окружении. Для срочного 001 отдельно сохранён текущий код функции и проверен контракт, но это не полный backup базы.

Пример запуска оператором после настройки PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSFILE и TLS (PGSSLMODE/PGSSLROOTCERT по официальным параметрам подключения):

```sh
RABOTA_BACKUP_ACK=READ_ONLY bash scripts/backup-db.sh /private/offsite/rabota-before-pr25
```

Использовать PostgreSQL client major 17 или совместимый новее сервера. Архив содержит чувствительные данные: хранить вне Git, шифровать при передаче/долгом хранении и проверить доступность второй копии. Роли/ACL проверять при восстановлении, не воспроизводить globals вслепую на managed-сервисе.

Проведена **синтетическая** репетиция `pg_dump → pg_restore`: восстановлены точные JSON-хеши строк основных таблиц, RLS шести основных таблиц и четырёх синтетических транспортных заглушек, request_id, запрет старого RPC и отказ пользователю без роли. `scripts/restore-local.sh` отказывается работать вне `127.0.0.1`, без маркера disposable и с БД, отличной от `rabota_restore`; непустую БД не перезаписывает. Это инструмент стенда, **не команда восстановления production**.

Логический архив БД не включает байты Storage, внешние секреты/настройки Vercel и конфигурацию платформы/функций. Реальные Auth/Storage/vault/extension зависимости проекта нужно отдельно проверить на восстановленной копии; fixture их полностью не моделирует. В этом же Supabase-проекте есть другие приложения: полный restore проекта затронет их и не может быть «откатом только CRM» без отдельной оценки.

Документация: [Supabase backups](https://supabase.com/docs/guides/platform/backups), [backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Free-план сам по себе не доказывает наличие доступного автоматического backup.

## 4. Точный порядок выпуска

1. Владелец отдельно разрешает только C1 либо весь план. До разрешения никаких production SQL/merge/deploy.
2. Зафиксировать текущие main/deployment SHA, актуальную схему и определения функций. Непосредственно перед применением повторить 000 (для срочного C1 — независимый guard 001). При drift остановиться.
3. Для полного релиза закрыть gate реального backup и восстановления, подготовить изолированный стенд с актуальной схемой. Прогнать тесты, затем реальный iPhone Safari/PWA. Preview, связанный с production, для тестовых записей не годится.
4. После отдельного подтверждения применить **001** от роли, имеющей право заменить функцию. Проверить определение/ACL только чтением. Тестовые оплаты в production запрещены. На этом срочный выпуск C1 может закончиться; frontend не нужен.
5. В согласованное окно попросить сотрудников завершить работу, не отправлять операции и закрыть старые формы. Сначала **002**, затем **003**. Между 003 и обновлением frontend старые финансовые формы и формы записи заказов намеренно получают отказ; чтение доступно. Не оставлять окно смешанной записи старых клиентов.
6. После отдельного разрешения на merge/deploy обновить frontend из PR №25. Серверная часть должна быть установлена **раньше** клиента, который вызывает v2. Не откатывать SQL автоматически, если выкладка frontend не удалась.
7. Открыть новую вкладку. Проверить чтение/вход owner, manager и master, кассу, календарь, лиды и ИИ без тестовых бизнес-записей. Сверить версии файлов/контракт. Первый настоящий платёж выполняется только как реальная деятельность владельца, не как тест агента.
8. Наблюдать ошибки отказа старым вкладкам, 5xx, таймауты/блокировки. Нужна отдельная проверка полномочий и JWT через настоящий PostgREST на стенде — тест SQL-role не заменяет весь сетевой путь.

## 5. Старые вкладки и повтор финансовой операции

Старый RPC больше не callable для authenticated после 003. v2 остаётся SECURITY DEFINER и вызывает ту же закрытую реализацию с правами владельца функции; это проверено тестом. Уведомления/чтение не используют этот RPC.

Новый клиент передаёт поколение 2 и ожидаемый updated_at на PATCH; прямые старые POST/PATCH заказов получают отказ до изменения строк. SECURITY DEFINER RPC оплаты/календаря сохраняют свои действующие проверки и обходят только REST-gate. Это не новая бизнес-роль и не замена RLS.

При потерянном ответе request_id сохраняется в localStorage до подтверждённого результата и повторно отправляется с теми же параметрами. 5xx/ошибка сети не удаляют ключ. Явный отказ транзакции 4xx позволяет начать заново. Изменённый payload с незавершённой операцией блокируется; сервер сверяет payload и возвращает исходный ID при повторе. Нельзя чистить localStorage, менять сумму или создавать новый ключ, пока неизвестный результат не сверен. Два разных сознательно подтверждённых действия с разными ключами не считаются одним автоматически.

Старый клиент после обновления страницы заменяется новым. Сохранить возможность старому клиенту продолжать финансовую запись и одновременно гарантировать идемпотентность невозможно: у старого запроса нет ключа. Отказ с обновлением страницы выбран как безопасный вариант.

## 6. Аварийный план

При ошибках после выпуска: остановить новые операции и после предусмотренного подтверждения применить `rollback-readonly.sql`. Он не удаляет строки, не очищает request_id и не возвращает NULL-уязвимость. Чтение остаётся доступным. Сохранить логи и текущий архив состояния; исправлять причину на стенде. Только после проверки совместимой версии разрешить записи через `resume-reviewed-release.sql`.

Старый production frontend можно вернуть лишь в режиме чтения: его финансовые вызовы и записи заказов блокируются 003. Удалять новые колонки/индексы, открывать старый RPC или возвращать уязвимые определения нельзя. Предпочтителен forward-fix совместимой версии.

Полное восстановление из backup — отдельная аварийная операция после оценки записей, появившихся **после** backup, Auth/Storage/секретов и других приложений проекта. Сначала восстановить копию в новом окружении, сверить строки и реквизиты, определить потери/перенос более новых законных операций. Прямой restore поверх production автоматически не выполняется. Данных, записанных после архива, в нём нет.

Итог: код и поэтапный план готовы к ревью. Срочный 001 можно рассматривать отдельно. **Без реального backup/restore gate, стенда PostgREST и iPhone весь релиз пока нельзя объявить безусловно безопасным.** Результаты CI — в Checks PR; ни один успешный синтетический тест не превращается в подтверждение реальных данных или платформенных зависимостей.

Полный production-контракт не публикуется в публичном репозитории. Автоматическая проверка отклонила его публикацию из-за внутренних политик/ACL; приватные файлы сохраняют результаты сверки. CI не моделирует все платформенные таблицы/политики — четыре транспортные таблицы являются явно помеченными заглушками.
