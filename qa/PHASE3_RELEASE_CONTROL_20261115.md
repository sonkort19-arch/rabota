## Gate перед каждым низкорисковым merge

1. Прочитать HEAD main и HEAD PR заново, `compare main...head`: нет отставания и неожиданных файлов; проверить diff и отсутствие влияния на платежи, роли, Auth, уведомления, секреты, инфраструктуру.
2. Убедиться, что оба CI jobs (`architecture`, `browser`) **completed/success на точном PR HEAD**. Pending/skipped/failure — не успех. Убедиться, что Vercel status относится к проекту `rabota`, не `grafik`.
3. Если diff безопасен, `mergeable=true`, нет неразрешённых конфликтов и нет регрессий, можно объединить. Затем проверить новый SHA main, push CI и Vercel commit status **на новом SHA**. Если после merge deployment pending, фиксировать pending, не писать «в production».
4. Любые изменения денег, RLS/ролей, Auth, клиентских уведомлений, финансового UI, API секретов и инфраструктуры — только отдельный review PR, без автономного production.
5. Записать SHA, ссылки на PR, CI и Vercel в `qa/autonomy-progress.json`. Если проверка не состоялась — оставить PR draft.

## Восстановление после неудачного кодового выпуска

- Перед merge сохранить предыдущий SHA main и номер PR. Не применять SQL-откат автоматически.
- При подтверждённой регрессии остановить дальнейшие merge и собрать симптомы/логи без персональных данных. Для **изолированного** ошибочного merge подготовить отдельную ветку от актуального main с `git revert -m 1 <merge_sha>` (для merge-коммита) либо `git revert <commit_sha>` (для обычного коммита). Это пример команды для локального review, **не** исполнять без проверки зависимых коммитов.
- Revert — новый PR с теми же CI, сравнением diff и Vercel target. Нельзя делать force-push/reset main или автоматически откатывать финансы, миграции и общую Supabase.
- После выпуска revert проверить новый main, CI, Vercel и основные пользовательские сценарии. Если откат безопасно не доказан — зафиксировать блокер и передать владельцу на решение.
