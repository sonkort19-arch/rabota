# Безопасный выпуск CRM «Работа»: этап 3 — права сотрудников

Дата аудита: 2026-11-14. Статус: **черновик, без применения к production**.
Ветка: `audit/release-step03-role-hardening-20261114` поверх PR #69 / #68.
Ничего не изменялось в production Supabase, Vercel, ветке `main`,
реальных заказах и реальном финансовом журнале.

## Подтверждённое состояние до изменения

Проект Supabase `yedzfmibceboncrytbqz` проверен запросами только на чтение.
`private.rabota_my_role()` возвращает роль исключительно активного
сотрудника из `rabota_members`.

| Возможность | Владелец | Менеджер | Мастер (Рауль) |
| --- | --- | --- | --- |
| Просмотр заказов | Все | Все | Только назначенные ему |
| Создание заказов | Да | Да | Только собственная запись по специальной RLS-политике |
| Редактирование заказов через REST | Да | Да | Нет |
| Принятие/выполнение своего заказа через RPC | Нет | Нет | Да |
| Отметка оплаты через RPC | Да | Да | Только своего принятого заказа |
| Распределение наличных | Нет | Нет | Только Рауль, свой заказ |
| Отметка сдачи наличных | Нет | Нет | Своё распределение |
| Подтверждение сдачи денег | Да | Нет | Нет |
| Списание / отмена ручной финансовой записи | Да | Нет | Нет |
| Запись зарплатной выплаты (до патча) | Да | Нет | **Да, себе** |
| Запись зарплатной выплаты (после патча) | **Да** | Нет | **Нет** |
| История начислений/выплат Рауля | Да | Нет | Да, в пределах RLS |

Важно: в production до применения PR #68 прямая установка `paid=true`
владельцем/менеджером через REST остаётся риском. Патч этого этапа сам по
себе не устраняет эту уязвимость: он зависит от PR #68.

## Изменения этапа 3

- `sql/009-owner-only-salary-payout.sql`: единственный изменяемый RPC
  `rabota_salary_payout_v2`. Только активный `owner` может создавать
  запись о зарплатной выплате; даже мастер с правильным UUID не может.
  Сохраняются блокировка строки мастера `FOR UPDATE`, проверка
  начислений, защита `request_id` и порядок учёта.
- В SQL перед изменением проверяются PostgreSQL 17, флаг
  `SECURITY DEFINER`, владелец функции и точный MD5 исходника из
  проверенного состояния базы. При несовпадении миграция прерывается.
- `money-workspace.js`: в кабинете мастера убрана возможность
  «Оформить выплату» и удалён соответствующий код модального окна.
  Баланс, начисления, история и экран собственных заказов остаются.
  Вместо кнопки — объяснение «Выплату проводит владелец».
- Владелец продолжает пользоваться существующей формой выплаты в
  `finance-payroll.js` и тем же RPC. Никаких операций с настоящими
  финансами при подготовке патча не выполнено.

**Отдельный запрос на зарплату с подтверждением владельца не создаётся**
на этом этапе. Рауль может обратиться напрямую; добавлять отдельный
процесс заявок можно после согласования требований и без смешивания
его с фиксацией фактического получения денег.

## Известные ограничения и вопросы до выпуска

1. В production этот SQL не применён. Необходима отдельная Supabase
   staging-среда с JWT и ролями, чтобы проверить PostgREST/RLS и UI.
2. Прежние ручные выплаты в журнале, в том числе проведённые мастером,
   не удаляются и не переписываются. Финансовая сверка из PR #69 ещё
   требует подтверждения по фактическим документам.
3. Процедуры `rabota_approve_master` / `rabota_provision_master` могут
   переназначать исторические заказы. При включении PR #68 любое
   изменение уже оплаченного заказа может быть заблокировано. До
   выпуска проверить утверждение новых сотрудников с такими заказами,
   не отключая защиту оплат.
4. Предупреждения Supabase Security Advisor о `SECURITY DEFINER`
   не означают автоматическую уязвимость каждой RPC. Права и
   внутренние role checks необходимо проверять отдельно; функции
   других приложений в общей базе не трогать.
   Документация: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable
5. Визуальные тесты на настоящем iPhone и конкурентные выплаты
   в отдельной Supabase ещё требуются.

## План выпуска / отката

- Подтвердить успешный CI, провести отдельный SQL review.
- Создать изолированную Supabase staging, протестировать роль каждого
  сотрудника; убедиться, что выплаты проводит только владелец.
- Перед production получить снимок базы и проверить восстановление.
- Применять только после проверенного PR #68 и отдельной команды
  «на основную». Патч не должен идти в production самостоятельно.
- Для отката вернуть проверенную старую функцию **только по решению
  владельца**, понимая, что это снова открывает возможность
  самостоятельного проведения зарплаты мастером. Предпочтителен
  forward-fix при подтверждённом дефекте.

Статус общего плана: этап 3 подготовлен к staging, но ещё
**не закрыт для безопасного production**.
